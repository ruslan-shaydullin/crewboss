## 0. Что это (одним абзацем)

Паттерн (+ тонкий Claude-Code-референс), который превращает профиль ролей кодящего
агента в **детерминированные гейты**, держащие границу не на «мы попросили агента
быть хорошим», а на физике конфигурации. Тезис: **всю должностную автономного
тех-лида можно загейтить ДВУМЯ механизмами + один слой честно НЕ гейтить — и прямо
об этом сказать.** Новизна не в механизмах (они заимствованы), а в их интеграции и
в интеллектуальной честности относительно того, что enforce'ится, а что нет.

## 1. Threat model — reliability, НЕ security (это и есть позиционирование)

Два разных «нулевых доверия», их постоянно путают:

- **Security-zero-trust** — недоверенный *ВВОД*: prompt injection, внешние данные,
  злонамеренный агент, утечка токена. Изъезжено: dual-LLM, CaMeL, capability-sandbox,
  guardrails. **ВНЕ scope этой спеки.**
- **Reliability-zero-trust** — недоверенное *ПОВЕДЕНИЕ* агента: он не злонамерен, но
  **ленив / over-eager / врёт «готово» / читает вопрос как команду / масштабирует на
  догадке**. **ЭТО наш scope.**

Практическое следствие, которое всё упрощает: раз агент не злоумышленник, нам не
нужны security-grade механизмы (изоляция токена, sandbox). Достаточно **более слабых,
но достаточных и полностью нативных** — потому что мы защищаемся от честного
переусердствования, а не от обхода.

## 2. Кор-идея: гейтить можно ДЕЙСТВИЯ, не СУЖДЕНИЕ

Нельзя hard-загейтить суждение («не читай вопрос как команду» — это RLHF, не
permission-правило). Можно загейтить только действия и заявления. Поэтому делим
профиль на **три слоя по тому, ЧЕМ каждый держится**:

| Слой | Что держит | Класс enforcement | Механизм |
|---|---|---|---|
| **1. Действия-эскалации** | спавн агентов, merge, push в общую ветку, авторство борда, пачка issue | **HARD** | identity + tool-allowlist (гвоздь 1) |
| **2. Заявления о готовности** | ложное «готово»/«исчерпано», close при недоделке, merge неодобренного | **HARD** | completion-gate на детерминированном пруфе (гвоздь 2) |
| **3. Диспозиция / суждение** | вопрос≠команда, самохвальство, «казаться продуктивным», классификация роутинга | **honestly SOFT** | прозой в системнике; НЕ enforce'им и не притворяемся |

## 3. Роли = launch-time identity (гвоздь 1)

Роль НЕ даётся по умолчанию / по чтению конфига / по инференсу. Она —
**детерминированный выбор на запуске** (vendor-neutral: «launch-time identity»;
Claude Code: `--agent <role>`). Чат-фразой роль сменить нельзя — это снимает
конфликт «фраза vs identity» (A2 в исходном профиле): «тех-лид не вызван» = просто
**default identity** (инструмента нет), а не «deny».

| Роль | Активация | Легит-инструменты | Эскалация (физически недоступна) |
|---|---|---|---|
| **dev-assistant** (default) | без префикса | Read/Edit/Write; commit+push своей `fix/`-ветки; `gh pr create` | груминг борда, спавн, merge |
| **Executor** | `--agent executor` | то же + `git branch task/<id>`, push своей task-ветки, worktree | push в общую ветку, merge, спавн, работа вне своей issue |
| **Task-helper** | `--agent task-helper` | Read; `gh issue view/edit/comment`, label | code-edit (нет Edit/Write); git-mutation — по мандату, не хуком |
| **Tech-lead** | `--agent tech-lead` | Read; `gh issue create/edit/comment`, labels, milestone, sub-issue; `gh pr view/diff`; `gh pr merge` (гвоздь 2). **Под Арх-2 НЕ спавнит** — executor'ов запускает лаунчер; tech-lead декомпозит (фаза-план) + ревью/мерж | те же действия БЕЗ явного вызова роли |
| **boss** | `--agent boss` (разговорный) | Bash → только `gh issue create/comment/edit` (чартеры) + read-only борд | merge, push, spawn, code-read/edit — **code-blind + exec-blind** |
| **analyst** | `--agent analyst` | Read/Bash (read-only расследование) + `gh issue comment` (findings-дайджест) | code-edit, merge, spawn — **read-only, цель делегирования** |

**Различитель легит-работы и failure-mode — единственный: был ли явный вызов роли.**
Identity его и кодирует детерминированно.

### 3.1 Две плоскости (граница = задача)
- **Разговорная (sync, чат):** `dev-assistant` («сделай вот это сейчас») и `boss`
  («решим ЧТО делать → чартер»). Человек думает с ИИ; борд не грызут.
- **Исполнительная (async, борд = I/O):** `tech-lead`, `executor`, `analyst`, `task-helper`
  (executor'ов запускает **лаунчер**, не tech-lead — Арх-2; analyst — вне цикла лаунчера,
  цель ad-hoc делегирования). Таск-driven: запустил →
  грызут борд → нет задачи = стоп. «Запустил и спишь».

Граница плоскостей — **задача/issue**. Гейты — это **цена** unattended-автономии: они и
делают «оставить грести без присмотра» доверяемым. `boss` стать `tech-lead` не может —
у него нет execution-инструментов (tool-absence рекурсивна: каждый уровень = только своё
+ право передать вниз).

### 3.2 Plan-approval loop (boss ↔ tech-lead)
Поток крупной цели: `boss` ставит **ЦЕЛЬ** (charter) → `tech-lead` **фаза-план**
(декомпозиция в parent + `- [ ] #N` sub-issues + обоснование, status `plan-review`) →
`boss` **аппрувит** (flip `approved`) → `tech-lead` **фаза-исполнение**.
- **Enforce (Арх-2):** пока charter не `approved`, его leaf-sub-issues НЕ launchable →
  лаунчер не запускает executor'ов (предикат `launchable.sh`; НЕ гейт спавна — спавна нет).
  ВТОРОЙ гейт (аппрув плана до старта) в пару к completion-gate после (§5.1).
- **Роли:** boss = WHAT + approve; tech-lead = HOW (decompose) + review/merge (исполняют executor'ы лаунчера).
- **Аппрувер:** boss (ИИ) на всём + человек ТОЛЬКО на крупном/необратимом (тугой триггер).
- **Честный предел:** ИИ-аппрув = коррелированные слепые зоны (ИИ судит ИИ) → поднимает
  ПОЛ (грубое under-scoping), не ПОТОЛОК. Ceiling — рубрика/диверс-линза в ревью boss'а +
  человек на крупном. **STATUS: plan-approval ПОСТРОЕН** (clause «charter approved» в предикате лаунчера, зелёный тест); scope-completion Stop-гейт — НЕ построен.

## 4. Два гвоздя (механизмы)

### Гвоздь 1 — identity + tool-allowlist
Нет инструмента в наборе роли → действие **физически недоступно** (не «агент решил
не делать»). Claude-Code-референс:
- **роль = `--agent <name>`** — верхнеуровневая сессия под идентичностью агента;
- **tool-allowlist в agent-файле (`tools:`)** — единственный локальный слой, который
  **держит даже против `bypassPermissions`**: нет инструмента в наборе → модель его не
  видит и не вызовет (проверено на v2.1.161);
- **командный уровень — центральный PreToolUse-хук, ветвящийся по `agent_type`**
  (stdin-поле, несёт имя `--agent`): «эта роль может `gh pr merge`, та — нет». Хук
  детерминирован: `canon()` сворачивает **внутри-модельные** варианты к литералу до матчинга
  (кавычки `gh pr "merge"`, `command`/`/path/gh`, global-flags `gh -R o/r pr merge`, REST
  `gh api …/pulls/N/merge`). Слипает только **намеренная evasion** (`gh${IFS}pr…`, `$VAR`,
  `eval`, alias) — adversarial, вне модели (§1: «не от обхода»). Это **friction-gate против
  честного переусердствования**, НЕ enforcement против evasion;
- порядок оценки `hooks → deny → mode → ask → allow`;
- **ЧЕСТНЫЙ ПОТОЛОК:** settings-`deny` И хук-deny **обходятся** `bypassPermissions` /
  `--dangerously-skip-permissions` — это человеческий escape-hatch, и агент сам его **не
  включит**. Верб-матчинг канонизирует внутри-модельные варианты, но **defeatable намеренной
  evasion** (`${IFS}`/`$VAR`/`eval`/alias — adversarial, вне модели, §1), а `gh pr merge --admin`
  пробивает branch protection → merge-якорю нужен **require-admins**. Твёрдо-против-bypass только tool-absence
  (`tools:`) и server-side GitHub branch protection (§5.2). settings-`deny` = defense-in-depth,
  не гарантия.

### Гвоздь 2 — completion-gate на детерминированном пруфе
PreToolUse-хук на **конкретном действии** отбивает его, пока не предъявлен
**детерминированный** пруф. Не self-report, **не LLM-судья** (корреляция ошибок
судьи и генератора делает это иллюзией проверки). Claude-Code-референс: PreToolUse-хук,
`exit 2` / `permissionDecision: "deny"` отменяет вызов до проверки mode. Команда-хук
(детерминированно), НЕ prompt/agent-хук (тот зовёт модель — это уже не гвоздь).

## 5. Proof-контракт (крукс слоя 2)

**Принцип якоря: пруф = объективное состояние GitHub на ТЕКУЩЕМ HEAD, никогда —
артефакт, который агент может отредактировать** (чеклисты `- [x]`, лейблы, свои слова).

Рекурсивная цепочка:

| Действие | Роль | Пруф (детерминированный) |
|---|---|---|
| объявить «PR готов» | Executor | verification-gate зелёный: required-чеки на head-SHA == passing (см. §5.2) |
| `gh pr merge` | Tech-lead | аппрув **не-автора** (`reviewDecision == APPROVED`) **+** green на head-SHA (см. §5.2) |
| `gh issue close` | Tech-lead | см. §5.1 — единственный чокпоинт (явный close; keyword-авто-close запрещён) |

### 5.1 Закрытие issue — единственный чокпоинт

**Путь закрытия — только явный `gh issue close` (агент). Keyword-авто-close
(`Closes #N` → server-side close при мерже в default-ветку) ЗАПРЕЩЁН:** он обходит
PreToolUse-хук и не срабатывает на не-default базе. Один контролируемый вход.

PreToolUse-хук на `gh issue close #N`:
1. **human-owned** (`type:human-*`: human-test / -decision / -setup …) → **DENY** (закрывает человек).
2. **есть открытые дети / неотмеченные `- [ ] #M`** → **DENY** (декомпозиция не завершена).
3. **лист с кодом** → **ALLOW** iff #N закрывает/линкует **смерженный PR**
   (гейтнутость гарантирована: мерж возможен только через merge-гейт).
4. **родитель, все дети закрыты** → **ALLOW**.
5. **аналитический деливерабл тех-лида** (`type:tech-lead`/`analysis`/`research`, без PR) →
   **ALLOW только при digest-пруфе** (коммент-маркер `crewboss-digest`). **SOFT:** доказывает,
   что дайджест предъявлен, НЕ что анализ верен (бьётся с матрицей «дайджест-пруф»).
6. иначе → **DENY** (нет пруфа).

> Уточнено и **проверено против реальных issue** (live gh): rule-1 ловит любую
> `type:human-*`-метку; rule-5 (digest-проксик) добавлен под аналитику тех-лида без PR.
> Live-прогон поймал баг детекции метки (jq `-e` по последнему значению стрима) — починен.

Под-кейсы:
- *Один PR → много issue* (`Closes #12, #13`): ок — обе наследуют гейтнутость
  смерженного PR, *скоуп* подписал ревьюер. Отдельный механизм не нужен.
- *Частичная работа*: НЕ гейтим — **проектируем прочь декомпозицией.** Лист не
  закрывают наполовину: закрывают полностью сделанную sub-issue её гейтнутым PR;
  родитель закрывается детерминированно (правило 4). Синергия декомпозиции и слоя 2.
- *Честный остаток (слой 3):* «полностью ли PR закрывает лист» — суждение; несёт его
  **аппрув ревьюера** (видит дифф + `Closes`-список) + soft-норма в системнике («не
  вешай `Closes` на частичный PR; не закрывай родителя из PR одного ребёнка»). Потолок
  = добросовестность ревьюера; математически «готово» не доказывается.

### 5.2 Источник истины «green» и свежесть

**Истина = required CI-status-чеки на head-SHA PR; merge-гейт якорим в GitHub branch protection.**
- *CI, не локальный прогон:* CI крутится в инфре GitHub, не на машине агента → агент не
  подделает (локальный прогон он может пропустить / подменить команду / прогнать на
  грязном дереве). Серверная правда — наш security-vs-reliability водораздел.
- *Branch protection = настоящий гвоздь:* «require approvals + require status checks +
  require up-to-date + **dismiss stale approvals**». Тогда `gh pr merge` физически не
  смержит несоответствующий PR (GitHub отбивает server-side); PreToolUse-хук — локальное
  зеркало (раньше/понятнее ошибка), не единственная опора.
- *Свежесть (анти-стейл):* всё привязано к **head-SHA** (`headRefOid`), не к «PR вообще»
  → старое зелёное на прежнем коммите не считается; «dismiss stale approvals» снимает
  аппрув при новом коммите → сценарий «одобрил → дослал код → смержил» закрыт.
- *Фоллбэк без CI:* хук гоняет verification-команду репо против **чистого checkout
  точного head-SHA** (не грязного рабочего дерева). Слабее (локально) — помечаем честно.
- *Анти-тампер:* определение verification-команды / список required-чеков живут в репо →
  ослабить гейт = изменить код = пройти gated-merge с аппрувом. Молча не ослабишь.
- *Честный предел:* сила гейта = какие чеки помечены **required**. «Green» = «required
  прошли на этом SHA», не «код верен».

**Анти-self-approve:** аппрувер обязан быть не-автором/человеком (branch protection +
required review). Иначе self-approve = тот же false-done на уровне мержа.

**Happy path vs гвоздь (важно):** «тех-лид создаёт задачу-на-аппрув и мержит по
получении» — это *поведение* (soft, в системнике). Гвоздь — это то, что merge
отбивается БЕЗ сигнала аппрува, **прошёл агент по-хорошему или попытался срезать.**
Гвоздь на действии, не в инструкции — в этом вся разница.

**Честный предел (не замалчивать):** green CI доказывает «заявленные чеки прошли на
этом коммите», НЕ «работа верна/полна». Ленивый агент напишет зелёные-но-пустые
тесты. Мы сдвигаем границу доверия со «слова агента» на «объективный гейт репо» —
большой шаг, но потолок гейта = качество тестов. «Stop-хук снижает false-done» —
**гипотеза из литературы, не измерено** на нашей версии; держим как гипотезу-к-проверке.

## 6. Роутинг human-decision (слой 3 + backstop)

Роутер срабатывает на **развилке** по ходу автономного захода и **после отчёта**
аналитика. Корзины:
- *техническое + обратимое + в компетенции + могу обосновать* → **решаю сам**
  (обоснование + «обратимо, оспоришь — переиграем»). Граница смелая: могу решить и
  откатить → **обязан** сам, не эскалировать;
- *продуктовое / необратимое / дорогое / values-trade-off* → **human-decision** (issue:
  варианты + рекомендация + «почему именно ты»);
- *отчёт неполный* → ещё аналитик-задача; *готово к стройке* → dev/agent-задача.

**Честно:** сама классификация «в какую корзину» — суждение, **слой 3, НЕ гейтится**
(хук-судья ошибётся так же, как агент). Детерминированно только:
1. **backstop через отсутствие капабилити** — по-настоящему опасное/необратимое
   (push в master, drop, смена биллинга, неодобренный merge) **отсутствует в
   allowlist'е любой роли**. Плохой роутинг не может вызвать плохое действие — агент
   **структурно** вынужден идти к человеку, не потому что мудр;
2. **эмиссия** human-decision issue — наблюдаемый `gh`-вызов.

Формула бренда: **«мы не enforce'им, что агент роутит мудро; мы enforce'им, что
действия, которые он мог бы зароутить плохо, ему недоступны.»**

| Task-helper | `gh issue edit/comment` | allow (тихо) | гвоздь 1 |

| Tech-lead | `gh issue create` ×N, milestone, sub-issue | allow (тихо) | гвоздь 1 |
| Tech-lead | декомпозиция в sub-issues (фаза-план) | allow (тихо) | гвоздь 1; **executor'ов запускает лаунчер, не tech-lead** (Арх-2) |
| Tech-lead | `gh pr merge` одобренного+green | allow | гвоздь 2 (аппрув не-автора + green) |
| Tech-lead | `gh pr merge` неодобренного | deny | гвоздь 2 |

| Tech-lead | `gh issue close` (no-code) | агент не закрывает | вне гвоздя 2 (человек) |

| на развилке | классифицировать decision | — | **soft (слой 3)** + backstop |
| любой режим | опасное/необратимое | недоступно | гвоздь 1 (нет ни у кого) |

## 8. Что эта спека ЯВНО НЕ делает (раздел бренда — не сокращать)

- **Не чинит диспозицию.** Вопрос≠команда, самохвальство, «казаться продуктивным» —
  слой 3, мягкий, лечится тренировкой, не правилом. Пишем «стараюсь», не «enforced».
- **Не гейтит суждение роутинга.** Только действия под ним.
- **Не делает гейт непробиваемым.** Потолок completion-gate = качество тестов; green ≠ correct.
- **Не держит против `bypassPermissions`.** Хуки и settings-`deny` обходятся человеческим
  `--dangerously-skip-permissions`; против него стоит только tool-absence (`tools:`) и
  GitHub branch protection. Агент сам в этот режим не войдёт — человек может, и тогда
  локальные гейты сняты. Говорим прямо.
- **Не защищает от injection / злонамеренного агента / утечки токена** — это
  security-zero-trust, другой проект (см. Threat model).
- **Не претендует на измеренный эффект** там, где есть только гипотеза из литературы.

## 9. Reference implementation — scope v0

**Шипаем (тонкий референс):**
- **5 agent-файлов** (`--agent`): Executor / Task-helper / Tech-lead / **boss** (code-blind+exec-blind) / **analyst** (read-only) + **dev-assistant = default** (без `--agent`, файла нет); tool-allowlist'ы;
- PreToolUse-гейты: `gh pr merge` (аппрув+green), `gh issue close` (закрыт-смерженным-PR),
  «PR готов» (green на HEAD);
- **лаунчер** (`reference/launcher/`): предикат launchable + цикл (poll→claim→worktree→`--agent executor`→review/blocked + retry-cap) — executor'ов запускает ОН (Арх-2), не tech-lead;
- демо на песочном GitHub-репо, где видно **блок** merge неодобренного и **блок**
  close без закрывающего PR (+ запись asciinema/видео, чтобы adoption не требовал прогона).

**Специфицируем, но НЕ кодим в v0:**
- gh-aw-style token-split (read-only агент + отдельный write-job) — **опциональный
  security-grade апгрейд**, не нужен для reliability;
- триаж/роутинг-логика — прозой в системнике;
- multi-level спавн / agent-teams (самая vendor-хрупкая поверхность — за флагом);
- **scope-completion Stop-гейт** — спроектирован, НЕ построен (plan-approval — ПОСТРОЕН: предикат лаунчера, §3.2).
