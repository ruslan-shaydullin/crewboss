# Расхождения плана «Анализ в петле» (#334) с реальной архитектурой

> Грунтовано разбором кода (HEAD `main` d094740, file:line). План НЕ правлен — здесь только что НЕ совпадает.

## Итог
Направление плана верное, но он местами **разъехался с тем, что УЖЕ есть**. Два главных:
(1) бОльшая часть «анализа в петле» уже построена в #131 — план считает её greenfield;
(2) фундамент «роли-из-конфига» сам непоследователен (4 пути резолва, 2 схемы) — план строит семейство аналитиков на шаткой базе.

---

## Расхождения

### D1 — C2 «вставить `claude --agent analyst`» = хардкод, и имя неверное (твой catch, глубже)
- План: вставить `claude --agent analyst`.
- Реальность: `claude --agent $ROLE` всегда берёт персону из `<work-tree>/.claude/agents/$ROLE.md` (spawn.sh:69). Имя передаёт лаунчер. Аналитик УЖЕ резолвится из конфига: `manifest_analysis_roles` → `org.json: analysis_roles:["solution-analyst"]` (launcher:980-983). Реальное имя — **`solution-analyst`**, не `analyst`.
- **Разъезд:** C2 — это НЕ «вставить хардкод-вызов», а «включить manifest-резолв на self-build-аналитика». «analyst» как литерал неверно — есть и loop-ops `analyst.md`, и manifest `solution-analyst.md`.

### D2 — C1 «построить механизм сходимости» = он во многом УЖЕ ЕСТЬ (#131) [большое]
- План: C1 строит механизм анализ↔план со сходимостью с нуля (bootstrap).
- Реальность: manifest-режим уже несёт полный пайплайн analyst → composition → cto/human-аппрув → tech-lead (launcher:957-1123). И он **ИТЕРИРУЕТ**: analyst↔cto через ре-роутинг лейблов по тикам (reject→needs-analysis→снова analyst), RETRY_CAP. Есть HD-2 cost-оценка + эскалация в `type:human-decision`.
- **Разъезд:** C1 НЕ greenfield. Существует: стадия аналитика, composition, аппрув-гейт, сходимость analyst↔approver. C1 надо переформулировать: «включить #131 для self-build + добавить НЕДОСТАЮЩЕЕ».

### D2b — «сходимость» в плане ≠ «сходимость» в коде
- План: итерация **analyst↔tech-lead** до согласия.
- Реальность: существующая сходимость — analyst↔**cto(approver)**; tech-lead ВНИЗ по потоку и **ОДНО-проходный** (launcher:1152-1166, skip-guard:971). analyst↔tech-lead-сходимости НЕТ.
- **Разъезд:** то, что план зовёт сходимостью (analyst↔tech-lead) — РЕАЛЬНО новое. А analyst↔approver уже есть. План смешал существующее и новое в один C1. Истинно-новое = analyst↔tech-lead plan-сходимость.

### D3 — «механический стаб» частично дублирует уже протестированное
- Реальность: существующий пайплайн уже покрыт тестами на стабах — `manifest-e2e` (полный прогон), `analysis-spawn`, `approval-gate` (CB_SPAWN-стабы).
- **Разъезд:** bootstrap-стаб C1 переоткрывает часть существующего. Стаб-first оправдан только для истинно нового (analyst↔tech-lead plan-сходимость), не для пере-сборки #131.

### D4 — ДВА аналитика, план не выбирает
- Реальность: `reference/.claude/agents/analyst.md` (loop-ops: `name/description/tools`, Read/Bash, read-only) И `team-example/roles/solution-analyst.md` (manifest: `name/kind/domain/tools/profile/code_blind`). Разные схемы фронтматтера.
- **Разъезд:** C2 «аналитик под самосборку» не говорит, какой из двух (или третий) и в какой схеме. Split-brain.

### D5 — «read-only» энфорсится не так, как подразумевает план
- Реальность: read-only держится тем, что Claude читает `tools:` из агент-файла — ТОЛЬКО если файл материализован в `.claude/agents/` (prep-spawn:338-343 manifest / 331-334 governed). Manifest-поле `tools:` (`manifest_role_field`) консумится ТОЛЬКО в тестах — в спавн/гейте не используется, работает лишь транзитивно через `cp` всего файла. Для стандартных ролей при `CB_GOVERNED≠1` tool-гейта НЕТ (только хук по имени + branch protection). `code_blind` Claude НЕ читает — он переимплементирован в хуке ПО ИМЕНИ (boss/cto).
- **Разъезд:** «все аналитики read-only» — не декларация-свойство. Нужно: manifest `tools:` + материализация + (для code-blind) запись в хук по имени. План это упускает.

### D6 — базового промпта НЕТ нигде, и босс даже не в петле
- Реальность: ни поля, ни файла, ни коммента с исходным промптом (grep пусто). Босс запускается ИНТЕРАКТИВНО (`bin/crewboss:162`), пишет чартер от руки; «промпт» вниз = тело issue (board-gh.sh `get prompt` → `.body`).
- **Разъезд:** C3 верен по сути, но недооценивает объём: нужен и #291 (захват промпта), и НОВАЯ схема хранения, и босс ещё не loop-wired.

### D7 — observer/test-planner есть, но в ДРУГОЙ системе ролей
- Реальность: `observer.md`, `test-planner.md` есть как loop-ops (`.claude/agents`), но НЕ в manifest `team-example/roles/`.
- **Разъезд:** если C1/C2 строят аналитика в manifest-системе (как solution-analyst), а C5/C8 ссылаются на loop-ops observer/test-planner — это два разных мира. План не выбирает одну систему для всего семейства.

### D8 — фундамент «роли-из-конфига» сам непоследователен [мета]
- Реальность (флаги разбора): **4 пути резолва роли** — manifest-policy (analyst/cto) / хардкод-литерал (tech-lead launcher:1165, git-resolver:1143) / file-existence (loop-ops) / issue-label (leaf executors). **2 схемы** фронтматтера. `_LOOP_AGENT_FILE` частично мёртв для стандартных ролей (prep-spawn:73 force-blank). `manifest_role_field tools` не консумится в проде.
- **Разъезд:** план строит семейство аналитиков НА непоследовательном фундаменте «роль-как-конфиг» (#269 реализован частично). Возможно, консолидацию ролей-конфигов надо сделать ДО/параллельно — иначе семейство усугубит split-brain.

### D9 — manifest-режим имел НЕЗАДЕПЛОЕННЫЕ рантайм-деп (ДОКАЗАНО живым прогоном B, 2026-06-18)
- Реальность: на боксе не хватало `manifest.sh` (lib, лежит в `reference/launcher/`, лаунчер ищет `$CB_HOME/manifest.sh`) И `composition-parse.sh` (`reference/runtime/`) — обоих, нужных manifest-пайплайну. Без них режим падает: manifest.sh → exit 65 «library not found»; composition-parse.sh → cto-гейт ЛОЖНО реджектит валидный состав как «invalid» (file-not-found → пустой вывод → reject).
- **Окончательно подтверждает контекст D2:** manifest-режим **физически не мог гоняться в проде** — только в тестах (где деп есть локально/через CB_MANIFEST_LIB). «41 analysis в логе» = тесты, не прод.
- **Разъезд:** план/C1 предполагает «включить #131 для self-build» как лёгкое — но это требует СНАЧАЛА выкатить незадеплоенные рантайм-деп (audit: какие manifest-файлы НЕ в `runtime-manifest.tsv` / не в deploy-наборе). Иначе включение падает на проде.
- **Доказано вживую:** после деплоя `manifest.sh` + `composition-parse.sh` (на тест-чартере #343, self-build манифест cto+solution-analyst+executor): `solution-analyst` заспавнился, выдал **валидный осмысленный состав** (executor-лист, est $0.05). Первый reject был ЛОЖНЫЙ (отсутствие парсера), НЕ логика аналитика. Анализ в петле на первой стадии — рабочий, при условии полного деплоя деп.

### D10 — аналитик галлюцинирует роли вне манифеста + reject-цикл БЕЗ потолка (ДОКАЗАНО живьём, прогон B)
- **Галлюцинация роли:** `solution-analyst` первый раз выдал валидный состав (`role: executor` — в манифесте ✓), но на поздних раундах **дрейфанул на `role: go-backend-dev`** — продуктовую роль team-example, которой НЕТ в self-build манифесте (cto/executor/solution-analyst). composition-parse → exit 4 «роль не в манифесте». Причина: `solution-analyst.md` + `rubric.json` (копии team-example) тянут продуктовый контекст, а промпт аналитика НЕ хард-листит доступные роли манифеста → аналитик гадает и берёт go-backend-dev из памяти/рубрики.
- **Reject-путь БЕЗ потолка:** reject (`team-review → needs-analysis`) роутится как **success** (tries сброшен) → аналитик пере-спавнится без лимита → **бесконечный цикл analyst↔cto-reject, жжёт спавны** (3 раунда за ~15 мин, рос бы вечно — заглушил руками). Это РОВНО «convergence bound», который юзер заложил в C1 — **подтверждено живьём, что без него = слив денег.**
- **Фикс (в C1):** (а) промпт аналитика ОБЯЗАН хард-листить ТОЛЬКО манифест-роли (+ self-build rubric, не продуктовый); (б) reject-путь обязан инкрементить потолок раундов → эскалация к человеку при не-сходимости.

### Итог прогона B (что доказано)
✅ **Анализ в петле на первой стадии — рабочий:** solution-analyst спавнится, читает чартер, выдаёт осмысленный состав; сходимость-машинерия (analyst→composition→cto-gate→reject/approve) фаерит. ❌ **End-to-end до cto-approve НЕ дошло** — заблокировано каскадом: 3 deploy/layout-гэпа (D9) + галлюцинация роли + отсутствие потолка (D10). Все блокеры — грунтованы живым прогоном, ни один не виден из плана. Эксперимент свою задачу выполнил: доказал жизнеспособность + нашёл реальные блокеры (= и есть содержание C0/C1).
