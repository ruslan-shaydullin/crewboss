# crewboss — UX-роадмеп (чтобы легко, удобно, приятно)

Не косметика. Это список реальных точек трения (часть поймали на собственном live-прогоне) +
что с ними сделать. Принцип: **гейты — это цена автономии; задача UX — чтобы цена не чувствовалась**,
не пряча при этом честный потолок (честность сама по себе — часть продукта).

> **Статус: P0 + ядро P1 РЕАЛИЗОВАНЫ.** Готов `crewboss` CLI (`init`/`doctor`/`status`/`approve`/`run`/роли/`try`/`teardown`,
> `reference/bin/crewboss`, smoke 15/15) и читаемый прогресс лаунчера со сводкой. Осталось — дашборд-полировка,
> онбординг/демо, таб-комплит (P2).

## Откуда взяты болевые точки (факты, не догадки)

| Что больно | Где словили |
|---|---|
| Установка многошаговая и легко забыть кусок (`permissions.allow`, chmod, лейблы, BP) | сетап live-песочницы — 4 ручных шага + 1 скрытый баг |
| Unattended-агент тихо ничего не делает без `permissions.allow` | live-прогон №1: «blocked pending approval», PR нет |
| Вывод лаунчера непонятный: `launch #3` и тишина, неясно сколько ждать | дословно: «нихуя не понятно сколько ждать и че происходит» |
| Не видно состояния борда одним взглядом (что launchable / в работе / на ревью) | приходилось вручную `gh issue list --json …` |
| Грабли окружения: commitlint subject >70, нет `delete_repo` scope, BP на private | по ходу всех коммитов/прогонов |
| Длинно печатать `claude --agent X` и полные пути к лаунчеру | каждый запуск |

## Три оси

### 🟢 Легко — снизить порог входа

- **`crewboss init`** — одна команда вместо §1 гайда: копирует `.claude/`, пишет `settings.json`
  **с `permissions.allow` уже внутри** (грабля unattended исчезает by default), `chmod +x`,
  заводит лейблы, опционально включает branch protection. В конце печатает «что дальше».
- **`crewboss doctor`** — пре-флайт-чек: есть ли `jq`/`gh`, auth + нужные scopes (`repo`,
  `delete_repo`), валиден ли `settings.json`, исполняемый ли хук, включён ли BP. Печатает
  не «ошибка», а **что именно починить**. Ловит все грабли из таблицы заранее.
- **Разумные дефолты** + live-sandbox как «попробовать за одну команду» (уже есть `setup-live.sh` —
  допилить в `crewboss try`).

### 🟡 Удобно — меньше ручного

- **CLI-обёртка `crewboss`** поверх `claude --agent …` и путей к скриптам:
  - `crewboss boss | tech-lead | executor | analyst` — запуск роли
  - `crewboss run [--once | --loop | --dry-run]` — лаунчер
  - `crewboss approve #N` — одобрить план чартера (флип `plan-review → approved` одной командой)
  - `crewboss board` / `crewboss status` — состояние борда (см. ниже)
  - `crewboss init | doctor | try | teardown`
- **Авто-конфиг**: `init` ставит `permissions.allow` сам → на грабли unattended больше не наступишь.
- **Таб-комплит** для ролей/команд.

### 🔵 Приятно — ясность, доверие, ощущение контроля

- **Читаемый прогресс лаунчера** (бьёт прямо в «нихуя не понятно»): вместо `[launcher L1] launch #3`
  и тишины — строка состояния по каждой задаче (`#3 executor working… 0:42`), heartbeat/спиннер,
  и **итоговая сводка** в конце (`✓ 2 PR открыто · 0 blocked · 1m48s`). Видно, что живо и сколько идёт.
- **`crewboss status` — дашборд борда** одной таблицей: что launchable, в работе, на ревью,
  заблокировано; какие PR ждут аппрува; на каком этапе чартеры. Одним взглядом «где мы».
- **Actionable-сообщения везде**. Хук уже подсказывает фикс (`… Launch: claude --agent tech-lead`) —
  это правильный паттерн; распространить на все deny и на ошибки лаунчера/пре-флайта: не «failed»,
  а «что делать дальше».
- **Превью + dry-run везде**: «вот что я сейчас сделаю» перед действием. Снижает страх автономии —
  человеку спокойнее «оставить грести без присмотра».
- **Онбординг**: `init` печатает next-steps; 5-минутный туториал на live-sandbox; короткое демо.
  Сильный сюжет для доверия — «прогнали свой паттерн на себе, он дважды поймал авторов на
  over-claim, а live-прогон нашёл config-баг». Честность = маркетинг.

## Приоритеты

- **P0 ✅ СДЕЛАНО:** `crewboss init` (с `permissions.allow`) · `crewboss doctor` · читаемый прогресс +
  сводка лаунчера. Эти три убирают 80% трения, что мы сами поймали.
- **P1 ✅ в основном:** CLI-обёртка `crewboss` (`run`/`approve`/`status`) + дашборд `status`. Осталась полировка
  дашборда (фильтры, ширины).
- **P2 (осталось):** онбординг/туториал/демо · таб-комплит · превью-режимы.

## ⚠ Главный footgun на продумать: установка / distribution / PATH

> Seeded 2026-06-05 — поймали на себе. Установка/запуск — самый острый источник трения; продумать к релизу,
> чтобы пользователю не приходилось с этим ебаться.

1. **PATH / discoverability.** `crewboss` нигде не на PATH из коробки → пользователь либо пишет полный путь,
   либо сам симлинкает. Хуже: отсутствие PATH толкает хардкодить абсолютный путь прямо в команды/доки — и он
   потом случайно коммитится (так и вышло у нас). → Ставить на PATH при установке (`init` предлагает симлинк /
   brew-tap / npm-bin / curl-installer). Доки зовут `crewboss`, не путь.
2. **Установка не в тот репо — тихий self-shot.** `crewboss init` ставится в ЛЮБОЙ репо, включая твоё боевое
   приложение, и молча: (а) включает гейт на обычных дев-сессиях, (б) ставит blanket `permissions.allow`
   (убирает подтверждения), (в) создаёт crewboss-лейблы на РЕАЛЬНОМ GitHub-борде. Один промах = выстрел в ногу.
   → `init` должен предупредить/спросить («загейтит сессии ЭТОГО репо + создаст N лейблов на owner/repo —
   продолжить?»); явное разделение «попробовать в песочнице» (`try`) vs «принять в репо» (`init`).
3. **`teardown` не зеркалит `init`.** `init` пишет в `settings.json` (tracked), а `uninstall.sh`/`teardown`
   чистит `settings.local.json` → полного отката нет. → teardown обязан точно реверсить init (добавки в
   settings.json + опционально снять созданные лейблы), чтобы «убрать» было так же легко, как «поставить».
4. **Видимость состояния.** `doctor` пишет `ready ✓`, но не делает явным, что зелёное = «crewboss активен здесь
   и гейтит тебя». → doctor/status должны проговаривать impact, не только галочки.

Принцип: поставить / попробовать / снести — тривиально и необратимо-безопасно; промах «не туда поставил» не
должен молча ломать реальный репо.

## ⚠ Лаунчер: мульти-роль + нормальный TUI (продумать)

> Seeded 2026-06-05. Тех-лид в чат-сессии отработал отлично (борд→декомпозиция на фактах→роутинг→стоп-гейт),
> но вывод: **с ним вообще не надо чатиться**, а лаунчер — «так себе, пользоваться неудобно». Три связанных вещи:

1. **Тех-лид — board-driven, без чата.** Сейчас тех-лид — ЕДИНСТВЕННАЯ роль, которую гоняешь руками/в чате, и
   он скатывается в диалог «(a) или (b)?». Решение **структурное**: запускать его **headless** (`claude --agent
   tech-lead -p …`) через лаунчер — там собеседника нет, поэтому он вынужден просто выложить план на борд
   (leaf-issue + justification + `status:plan-review`) и остановиться. Аппрув — флипом лейбла на борде, НЕ в чате.
   Headless-запуск убирает Layer-3-срыв в Q&A структурно, а не промптом.
2. **Лаунчер запускает И тех-лидов, И исполнителей** (расширить однозадачный лаунчер до Арх-2-полного):
   - чартер в `status:needs-plan` → запустить **tech-lead** (Phase 1: декомпозиция → план на борд → стоп);
   - approved-листья → запустить **executor'ов** (как сейчас).
   Разные success-контракты: тех-лид → «leaf-issue созданы + `plan-review`» (не PR); executor → PR. `handle_result`
   надо разветвить по типу запуска. Это закрывает последний ручной шаг — «борд = I/O, запустил-спишь» для ВСЕХ
   ролей (Арх-2-дизайн: см. `board-orchestration.md`).
3. **Лаунчер — нормальный терминальный UI/UX (TUI), не голый poll-loop.** Сейчас это скрипт с env-переменными —
   неудобно. Нужен интерактивный терминальный интерфейс: **живой вид борда** (чартеры / launchable / в работе /
   ревью / blocked), **переключатели режимов** (executor-only ↔ tech-lead+executor, dry-run, once ↔ loop),
   **кнопки** run / pause / kill / approve-#N, **видимые и редактируемые настройки** (concurrency / budget /
   retry / poll), прогресс по задачам в реальном времени. НЕ веб-GUI (против «тонкого нативного») — именно TUI.
   Под капотом — тот же лаунчер + предикат + гейты; меняется только обвязка управления.
   - **Дашборд работающих агентов (live):** отдельный вид «что прямо сейчас крутится» — по каждому активному
     executor'у/тех-лиду: задача #N, ветка `task/N`, фаза (пишет код / открывает PR / done), elapsed, PID.
     Обновление в реальном времени. (На живом прогоне сразу видно зачем: крутилось 15 агентов — без такого вида
     непонятно, кто где и кто завис.)
   - **3 типа отображения, переключаемые в настройках** (+ хоткей для смены на лету):
     (1) **компактный** — строка на агента (`#80 · task/80 · 0:42 · пишет код`);
     (2) **таблица/грид** — колонки (issue / ветка / фаза / elapsed / PR), сортируемая;
     (3) **подробный** — карточка на агента: заголовок задачи + хвост лога / последнее действие.
     Выбор вида — настройка по умолчанию + переключение прямо в TUI.

## ⚠ Пер-чартерная релизная (интеграционная) ветка — продумать

> Seeded 2026-06-06 — поймали на live-прогоне. После прогона на develop повисло **15 PR разом** (#81–95),
> и это странно: develop засран, чартер целиком не отревьюишь (15 разрозненных PR вместо одного), а
> cross-PR конфликт (#82↔#83 — два PR переписывают одни файлы с разной политикой порчи данных) приземлился
> бы прямо в общий ствол. Идея: **каждый чартер живёт в своей ветке, в develop вливается ТОЛЬКО целый,
> отревьюенный чартер.**

**Суть.** Сейчас executor'ы ветвятся от develop (`task/N`) и открывают PR сразу В develop. Предложение:
при создании/одобрении чартера от develop отрезается **интеграционная ветка чартера** (`charter/<N>`).
Executor-листья ветвятся от `charter/N` и открывают PR **в `charter/N`**, не в develop. Когда все листья
влиты в `charter/N` и чартер отревьюен **как одна ветка / один диф** — открывается **один** PR
`charter/N → develop`, и уже он ревьюится/мержится.

**Зачем:**
1. **develop чистый** — туда падают только целые, проверенные чартеры, а не 15 полуфабрикатов.
2. **Ревью на уровне чартера** — одна ветка / один диф вместо N разбросанных PR. Видно чартер целиком.
3. **Cross-PR конфликты ловятся и решаются ВНУТРИ ветки чартера** до касания ствола (#82↔#83 разрулился бы
   в `charter/N`, develop бы не пострадал).
4. **Атомарность** — отменить чартер = удалить ветку. Чёткий маппинг чартер→ветка.

**Что продумать (открытые вопросы):**
- **Когда резать ветку** — при создании чартера (boss) или при аппруве плана (tech-lead)? Скорее при
  аппруве — execution стартует именно тогда.
- **Откуда лаунчер/предикат знают базу** — поле `Base: charter/N` в теле чартера? `task/M` ветвить от него.
- **Двухуровневый merge-гейт:** leaf-PR → `charter/N` (как сейчас: non-author approve + green) И
  charter-PR → develop (ревью всего чартера). Тот же `#96` reviewer-identity всё ещё нужен для финального влития.
- **Stale-base внутри ветки** — листья от `charter/N` ребейзятся по мере влития соседних (как сегодня, но
  локализовано в ветке, не в develop).
- **Depends-on ordering** остаётся, просто внутри `charter/N`.
- **Кто открывает финальный `charter/N → develop` PR** — tech-lead (review-pass), мерж — по гейту.
- **Нейминг:** `charter/N` vs `release/charter-N`; develop остаётся trunk.

Связано с «лаунчер мульти-роль» выше: именно лаунчер при запуске tech-lead/executor'ов и отрезал бы/знал бы
базовую ветку чартера.

## Чего НЕ делать (анти-цели)

- **Не строить веб/GUI-дашборд раньше CLI** — оверкилл и против «тонкого нативного референса».
  Терминальной таблицы достаточно.
- **Не прятать честный потолок ради «гладкости»** — «этот слой friction, эти два enforcement» должно
  оставаться на виду. Это доверие, а не баг UX.
- **Не плодить конфиг-флаги** без реальной нужды — каждый новый параметр = новая точка ошибки.
- **Не превращать `crewboss` CLI в обязательный слой** — голые `claude --agent` + скрипты должны
  продолжать работать; обёртка лишь удобство.
