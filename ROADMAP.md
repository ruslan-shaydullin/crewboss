## Что осталось — приоритизировано

### P1 — Charter-branch flow + роль integrator (ревью = чартер целиком, НЕ куски) 💲
Договорено 2026-06-11 (юзер). Человек ревьюит ОДИН PR всего чартера, не отдельные листья. Эмпирика:
догфуд-прогон #1 дал 6 leaf-PR прямо в main; 5 UI-листьев чартера #2 столкнулись по общим файлам
(App.tsx/styles.css/api.ts → 4 конфликта). Вручную собрано `charter/1` (#19), `charter/2` (#18/#20/#21,
зелёные), #22/#23 завёрнуты на rebase. Что построить:
- ☐ лаунчер на approved-чартер создаёт интеграционную ветку `charter/C`; leaf executors берут ветку ОТ неё и PR-ят В неё (не в main);
- ☐ **новая роль `integrator`/tester (ДОЛГ, юзер 2026-06-11): «смотрит чартеры и решает конфликты»** — проверяет чистое влитие каждого листа в `charter/C` + зелёный CI на интегрированном дереве; конфликт → лист на `needs-rework` (rebase на свежий `charter/C`, конфликт решает автор кода); петля сходимости;
- ☐ гейт перед человеком: tech-lead + boss сверяют `charter/C` с **критериями чартера** → только тогда один PR `charter/C → main`;
- ☐ merge-гейт: leaf→charter путь (аппрувер = integrator) отдельно от charter→main (человек);
- ☐ **UI (долг, юзер 2026-06-11): открыть PR чартера (`charter/C → main`) прямо из веба** + кнопка «решение» по чартеру → варианты: «проверить результат на продукте» / «влить в основную ветку»;
- ☐ **UI (долг, юзер 2026-06-11, приоритет): отдельная вкладка «задачи на человека»** (`type:human-decision`) — сгруппированы по чартерам; задачи без чартера — отдельный блок. Сейчас human-decision-issue на борде не видны в вебе никак;
- ☐ **критерии-всегда — под-анализ №1** (юзер: «самое важное», но «сходу не делать»): без заданных acceptance integrator меряет только «влилось+CI», не «то ли построили». Отдельный заход, дизайн через brainstorming→план.
- ☐ **Паттерн «разделённая диагностика» (диагноз ≠ фикс) — reliability-zero-trust, применённый к ДИАГНОЗУ (юзер 2026-06-11, после бага «карточки дёргаются»):**
  - ни один узел не диагностирует-и-чинит одновременно: диагностическая стадия физически отделена от фиксящей (tool-absence у диагноста, как у топов нет кода);
  - диагностика = **панель РАЗДЕЛЁННЫХ ролей, каждая смотрит ОДНУ узкую линзу** и выдаёт ТОЛЬКО своё видение в рамках роли, не фикс (для UI-бага: рендер/lifecycle · CSS/layout · state/data-flow · воспроизведение/поведение). Узлы **un-correlated** — изолированы, не видят выводов соседей (анти-group-think);
  - корневая причина установлена ТОЛЬКО когда **воспроизведена/подтверждена** (не «правдоподобна»); фикс дозволен лишь на подтверждённую причину;
  - фикс закрывается ТОЛЬКО подтверждением против воспроизведения бага («больше не воспроизводится»), а не «сделал, что в брифе»;
  - для UI одна из линз = **поведенческий прогон (headless-браузер)** — это и есть машинная проверка «визуальных» критериев (тот баг ловился бы машинно: «на idle-тиках ни один `.task` не получает transform»).
  - **Зачем:** без этого integrator («merge clean + CI green») и «критерии-всегда» сами пропускают false-done — все гейты зелёные и врут; человек (самый дорогой узел) вырождается в ловца багов по кругу. Один агент, диагностирующий-и-чинящий, = коррелированное доверие к своему поведению (именно так был спален человеческий ресурс на угадайку).

**Долг из верификации charter/2 (юзер 2026-06-11):**
- ☐ **«Обсуждение чартера/задачи при создании» + роль-фасилитатор (САМОЕ ГЛАВНОЕ, юзер)** — при заведении чартера/задачи интерактивное окно-чат, через которое можно обсудить замысел; нужна отдельная роль, которая в этом помогает (уточняет, предлагает, формализует в acceptance). Связано с критериями-всегда.
- ☐ **«Активный чартер» = автодрайв до PR** — кнопка-статус на чартере: пока активен, ВСЕ роли работают над чартером до блокера, пока не кончится лимит или весь чартер не упрётся в блокер. _(Уточнено 2026-06-11 после ревью #33: тонкую Run-кнопку из charter/33 УБРАЛИ — вводила в заблуждение. «Правильный Run» = (1) автодрайв plan→approve→execute, (2) **видимый прогресс в UI** — сейчас лаунчер пашет в фоне, дашборд молчит (ни «планирую…», ни агента в рейке), (3) **charter-aware спавн** — проверено: Run-флоу гонит default main-based spawn → лист тестового #56 ушёл PR'ом в main, не в charter/56. Плюс: **чартер нельзя открыть** с борда (карточки не кликаются в drawer) — отдельный UI-пробел.)_
- ☐ **Чеклист-драйвер (тех-долг, низкий приоритет, юзер 2026-06-11):** executor отмечает acceptance через `set-check` ПО ХОДУ (сейчас чеклист read-only, set-check живой, но никто не заполняет → всегда пустой).
- ☐ **Кнопка «запустить» у нового чартера** (сразу после создания — не надо отдельно дёргать лаунчер).
- ☐ Drawer: **история «что именно выполнено по задаче» + интерактивный чеклист задачи** (в связке).
- ☐ Discussion: **удаление комментария**.
- ☐ **BUG (#20, charter/2): модалка создания не закрывается по «Создать»**; всплывающий confirm бессмысленен — нужен **summary создаваемого + кнопка «редактировать»** перед подтверждением, и закрытие окна по успеху. (Тот же баг у task и charter форм.)
- _(сделано в charter/33: вкладка human-decision, удаление коммента, история+чеклист, кнопка запуска, summary+edit — влиты в main отдельным батчом; багфикс модалки + дёрганья тоже в main.)_

### P1.5 — Operability / автоматизация ручного труда (ДОЛГ, юзер 2026-06-11: «то что делаешь руками — записать в задачи») 💲
Всё, что я (оператор) делаю РУКАМИ в каждом прогоне — система должна делать сама. Сейчас не делает → записано:
- ☐ **КРИТ: бокс↔репо расхождение.** Весь боевой EC2-рантайм и ВСЕ фиксы сессии живут ТОЛЬКО на боксе (`~/cbnet/`), в репо их НЕТ: `crewboss-spawn.sh`, `crewboss-launcher-gh.sh`, `crewboss-prep-spawn-gh.sh`, `charter-leaf-prep.sh`, `rework-prep.sh`, `proxy.py` (с npm-allowlist), `claude.kafel` (xattr/io_uring/pkey), `board-gh.sh`, `start-stack.sh`. Бокс = единственный источник правды + единственная точка отказа (умрёт бокс — фиксы потеряны). Бэк-портировать в `reference/`, провижн собирать из репо.
- ☐ **charter-branch flow = прототип `charter-leaf-prep.sh` (box-only).** Лист берёт ветку ОТ `charter/C`, PR-ит В неё; `charter/C` создаётся от main под flock первым листом. Свернуть в лаунчер (это и есть P1 charter-branch механика, рабочий прототип уже есть — не проектировать с нуля).
- ☐ **Integrator-механики, которые я делаю руками:** разрешение конфликтов листьев (additive union), **закрытие leaf-issue при merge в charter/C** (GitHub НЕ авто-закрывает «Closes #N» при merge в не-default ветку → депенденты не разблокируются сами), прогон поведенческого гейта (headless) перед charter→main. Всё это — работа роли integrator.
- ☐ **Лаунчер не скоупится на один чартер** — берёт ВЕСЬ борд (схватил cruft #24 + чужой charter #1); пришлось руками вешать `hold` и закрывать junk. Нужен «прогон лаунчера, ограниченный одним approved-чартером / набором».
- ☐ **Поведенческий харнесс в репо + CI:** `repro.mjs` (дёрганье: «на idle ни один `.task` не получает transform») + `smoke.mjs` (загрузка, вкладки, 0 console-ошибок) — сейчас гоняю руками из `/tmp/cb-repro`; должны лежать в `ui/app/scripts/` и быть гейтом integrator'а (леафы #33 уже начали класть свои `scripts/*` — первый становится харнессом).
- ☐ **Operator-toil / хрупкость:** API-процесс зависает / плодит инстансы / дерётся за порт (нужен супервизор или `cb api restart` через kill-by-port, НЕ pgrep); ssh-туннель отваливается (нужен autossh/авто-реконнект); grep-маркеров в гейте исключал `*.css` (закоммиченные маркеры прошли зелёными — расширить на все файлы); **`pkill -f`/`pgrep -f` self-match** в скриптах (паттерн ловит мою же ssh-команду и убивает шелл — бить по PID/порту, не по строке); **API-деплой:** правка api.py в charter/ветке НЕ доезжает до бокса сама → «unknown action» в UI (нужен авто-деплой api.py из смерженной ветки).
- ☐ **kill_switch-гигиена (находка ревью #33):** я остановил лаунчер, оставив флаг `kill_switch` → каждый последующий Run молча глох («kill-switch present → stop»), юзер видел «нихуя». Run/старт лаунчера ДОЛЖЕН чистить kill_switch (или UI показывать «лаунчер заглушён kill-switch»). Состояние лаунчера (flags) — видимым в UI.
- ☐ **Предикат launchable не фильтрует `type:human-decision`** (находка #33): лаунчер считал human-decision-issue (с `Charter:`) launchable → запустил бы executor на человеческую задачу. Предикат должен брать только `type:agent`-листья.
